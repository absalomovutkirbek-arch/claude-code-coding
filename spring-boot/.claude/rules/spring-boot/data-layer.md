# Spring Boot: data layer (repositories, entities, migrations)

## Repository

```java
public interface WalletRepository extends JpaRepository<Wallet, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select w from Wallet w where w.id in :ids order by w.id")
    List<Wallet> lockByIds(@Param("ids") Collection<Long> ids);
}
```

- One repository per aggregate root, in `repository/`. It is a Spring Data interface; add a custom implementation (`<Entity>RepositoryCustom` + `Impl`) only for Criteria or native queries that `@Query` cannot express.
- Method vocabulary: `findBy...` returns `Optional<Entity>`, `listBy...` returns `List`, `pageBy...(…, Pageable)` returns `Page`, `existsBy...` returns `boolean`, `lock...` loads with `PESSIMISTIC_WRITE`, plus the inherited `save` and `delete`.
- Method names describe the business question (`findActiveByCustomer`). Use `@Query` with JPQL once a derived name needs more than two conditions.
- Parameters are always bound (`:name`). Never concatenate input into JPQL or SQL. Native queries only when JPQL cannot do it, with a comment saying why.
- Optional filters: `(:status is null or t.status = :status)`. For more than three optional filters use `Specification` or a custom implementation.
- Row locks: `@Lock(PESSIMISTIC_WRITE)` with `order by id` to avoid deadlocks. They work only inside the service's transaction.
- Load what the use case needs in one query: `join fetch` or `@EntityGraph`. Collections never trigger per-row queries.
- No `@Transactional`, no business decisions, no security context in repositories. `@Modifying` bulk updates are allowed for real bulk operations and are called from a transactional service method.
- Translate a unique-constraint `DataIntegrityViolationException` into `ConflictException` in the service when the conflict is a business case.

## Entity

- `@Entity` + `@Table(name = "<table>", schema = "<module>")`. Every column mapped with an explicit `@Column(name = ..., nullable = ..., length = ...)` that matches the migration.
- `@Id @GeneratedValue(strategy = GenerationType.IDENTITY) private Long id;`
- A `protected` no-argument constructor for JPA, and static factories that create a valid entity (`Transfer.completed(...)`). No public setters for everything: expose small state methods (`debit(amount)`, `markReversed()`) that touch only the entity's own fields.
- Enums: `@Enumerated(EnumType.STRING)`. Never `ORDINAL`.
- Timestamps: `Instant` with `@CreationTimestamp` / `@UpdateTimestamp`.
- `CHAR(n)` columns need `@JdbcTypeCode(SqlTypes.CHAR)`, otherwise schema validation fails at startup.
- Associations are `LAZY` (`@ManyToOne(fetch = FetchType.LAZY)`). No `EAGER`, no `CascadeType.ALL` without a stated reason, no bidirectional association unless both directions are used.
- Entities of other modules are referenced by ID (`private long ownerId`), never by association.
- Forbidden: business rules, repository or service access, `@PrePersist`/`@PostPersist` callbacks with side effects, `equals`/`hashCode` over all fields, Lombok `@Data`.

## Migrations (Flyway)

- Plain SQL in `src/main/resources/db/migration/<module>/V<yyyyMMddHHmmss>__<snake_case_name>.sql`. The timestamp version avoids collisions between modules and branches.
- The first migration of a module starts with `CREATE SCHEMA IF NOT EXISTS <module>;`. Table names are always schema-qualified.
- Flyway is forward-only: there is no down script. A wrong migration that is already committed is fixed by a new one. A hook blocks edits to committed migrations, and Flyway's checksum validation would stop the application anyway.
- Types: `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY`, `BIGINT` for references, `TIMESTAMPTZ NOT NULL DEFAULT NOW()`, `VARCHAR(32)` plus a `CHECK` listing the enum constants, `BIGINT` minor units or `NUMERIC(19,4)` for money.
- Every foreign key is declared with an explicit name and delete rule and has an index. Constraint names follow `common/database.md`.
- One logical change per migration. Schema and data changes in separate files.
- After writing a migration, update the entity so that `ddl-auto=validate` passes. Running the application or the API tests applies pending migrations to that database; against anything but the local or test database this requires the developer's confirmation.
